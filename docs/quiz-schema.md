# Контракт данных квиза

Этот файл — граница между контентом и приложением. Приложение не должно знать ничего о конкретных вопросах, только о схеме.

## Структура репозитория

```
/data
  rn-architecture.json
  rn-performance.json
  js-core.json          # позже
  ...
/docs                   # этот контракт и исходные md-файлы вопросов
/scripts                # валидация данных, запускается в CI
/src                    # приложение
```

Приложение находит темы глобом по `/data` на этапе сборки. Имя файла обязано
совпадать с полем `topic` внутри него — это проверяет валидатор. Добавление
темы = один новый файл и коммит, правок в коде не требуется.

### `topics.json` — порядок и группировка

Файл необязательный и **не является источником тем**: он задаёт только то,
чего нет внутри самих файлов — порядок и разбиение на группы на экране выбора.

```json
{ "topics": [
  { "topic": "js-core", "title": "JavaScript Core", "group": "Основы", "order": 1 }
] }
```

| Поле | Обяз. | Описание |
|---|---|---|
| `topic` | да | Должна существовать тема `data/<topic>.json` |
| `title` | да | Обязан совпадать с `title` внутри файла темы |
| `group` | нет | Заголовок группы на экране выбора |
| `order` | нет | Позиция в списке; значения не должны повторяться |

Тема, которой в реестре нет, всё равно попадает в приложение — просто в конец
списка и без группы. Ошибка только в обратную сторону: реестр ссылается на
несуществующую тему, спорит с ней о названии или дважды занимает один `order`.
Всё это проверяется валидатором.

## Формат файла темы

```json
{
  "topic": "rn-architecture",
  "title": "React Native: архитектура",
  "version": 1,
  "questions": [ ... ]
}
```

## Схема вопроса

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | string | да | Уникален глобально. Формат `<topic-slug>-NNN`. **Не переиспользовать** после удаления вопроса — прогресс пользователя привязан к id |
| `topic` | string | да | Совпадает с `topic` файла |
| `type` | enum | да | `single` \| `multi` \| `code-output` \| `open` |
| `question` | string | да | Markdown. Может содержать блок кода |
| `options` | string[] | для single/multi/code-output | Markdown-строки |
| `correct` | number[] | для single/multi/code-output | Индексы правильных вариантов. Для `single` ровно один элемент |
| `explanation` | string | да | Markdown. **Главное поле** — именно оно работает как карточка при повторении |
| `followUp` | string[] | нет | «Куда копнут дальше» — показывать после ответа |
| `difficulty` | 1\|2\|3 | да | 1 — база, 2 — уверенный уровень, 3 — сеньорный |

### Про `type: "open"`

Вопрос без вариантов — пользователь отвечает себе вслух, потом открывает `explanation` и сам оценивает: «знал / частично / не знал». Самооценка идёт в тот же прогресс, что и обычные вопросы. Это самый полезный тип для подготовки к собеседованию, поэтому режим «показать ответ» должен быть в один тап.

## Прогресс

Хранится отдельно от контента, ключ — `id` вопроса. Запись плотная: значение
CloudStorage ограничено 4096 байтами на ключ, а развёрнутый объект с
`lastAnswer` в ISO съедал бы около 90 байт на вопрос — лимит упирался бы уже
на четвёртом десятке.

```json
{ "v": 1, "d": { "rn-arch-004": [2, 3, 2, 20709] } }
```

Кортеж — `[box, seen, correct, day]`:

| Позиция | Поле | Описание |
|---|---|---|
| 0 | `box` | Коробка Лейтнера, 1..5 |
| 1 | `seen` | Сколько раз вопрос показывался |
| 2 | `correct` | Сколько раз отвечен верно |
| 3 | `day` | День последнего ответа — дни от эпохи по локальному времени |

`v` — версия формата. Кусок с чужой `v` при чтении пропускается, а не ломает
загрузку. Выходит около 35 байт на вопрос, то есть ~110 вопросов на ключ.

День хранится числом, а не датой, потому что интервалы считаются в
календарных днях: «завтра» наступает в полночь, а не через 24 часа.

### Повторение по Лейтнеру

5 коробок, интервалы в днях по номеру коробки: **0 / 1 / 3 / 7 / 21**.
Верный ответ поднимает на одну коробку (максимум — пятая), неверный сбрасывает
в первую. Вопрос пора повторить, когда `day + интервал(box) <= сегодня`;
вопрос без записи доступен всегда.

Интервал первой коробки равен нулю — то есть ошибочный вопрос доступен в тот
же день. Чтобы это не превращалось в бесконечный цикл, очередь повторения
берёт каждый вопрос **не больше одного раза за сессию**.

### Хранилище

`Telegram.WebApp.CloudStorage` с фолбэком на `localStorage` — приложение должно
открываться и в обычном браузере.

Ключи: `progress_<topic>__<N>`, где `N` — номер куска с нуля. Подчёркивание, а
не двоеточие: CloudStorage допускает в ключах только `A-Z`, `a-z`, `0-9`, `_`
и `-`. Прогресс разбит по темам, и тема при переполнении переливается в
следующий ключ. Куски самодостаточны: порядок чтения неважен, потеря одного не
ломает остальные.

Запись отложенная — ответы копятся и уходят одним пакетом: CloudStorage ходит
по сети, писать на каждый ответ дорого. Несохранившееся остаётся в памяти и
уезжает следующим сохранением.

### Незаконченная сессия

Отдельный ключ `session_current`, не связанный с прогрессом:

```json
{ "v": 1, "t": "React Native: архитектура", "q": ["rn-arch-001", "…"], "r": [1, 0] }
```

`q` — очередь вопросов в порядке показа, `r` — уже данные ответы. Точка
возврата равна длине `r`, то есть первому неотвеченному вопросу: сам ответ
попадает в прогресс сразу, поэтому вернуть человека на разобранный вопрос
значило бы засчитать его дважды.

Вся очередь лежит в одном ключе, поэтому у неё есть потолок: самая длинная
сессия — повторение по всем темам сразу. На 220 вопросах это около 2.8 КБ при
лимите в 4 КБ, то есть запас кончится примерно на трёхстах вопросах. Дальше
сохранение начнёт пропускаться (с предупреждением в консоли), и очередь
придётся разбивать на несколько ключей — так же, как это сделано для прогресса.

Сессия стирается, когда дойдена до конца, и не восстанавливается, если хоть
один сохранённый `id` исчез из банка: номера вопросов уже не те, а молча
подставить другой вопрос хуже, чем начать заново. Это прямое следствие правила
«не переиспользовать `id`» из раздела про добавление контента.

## Режимы приложения

1. **Квиз** — вопросы темы подряд, результат в конце
2. **Повторение** — только то, что пора повторить по `box`, вперемешку из всех тем
3. **Работа над ошибками** — где `correct / seen` ниже 0.6, при условии что вопрос показывался хотя бы дважды: по одному промаху судить рано

## Правила добавления контента

- Новый вопрос — только добавление в массив, без изменения существующих `id`
- Изменил смысл вопроса — новый `id`, старый удалить
- `version` файла повышать при любом изменении, приложение может показывать это в отладке
- Валидация: `correct` не выходит за границы `options`, `id` уникальны — имеет смысл проверять в CI
